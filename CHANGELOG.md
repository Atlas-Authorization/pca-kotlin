# Changelog

## Unreleased (0.5.0, action kit)

- **Breaking** (K5, secure default): `plan_root_authorized` is enforced by default. With no plan source (no `plan = "single-step"`, no context `plan` + `plan_authorized`, no `plans` registry) the check now FAILS with `plan_root_authorized: default-deny: no authorized plan is configured for this verifier (supply the plan and its authorization, or set insecureSkipPlanRootCheck)` instead of reporting `not-enforced`. `Authorize` has no opt-out (the check was already required, so the outcome is still a deny; only the reason text changed). This SDK has no lower-level verifier that computes the check, so no `insecureSkipPlanRootCheck` option exists here.

- Added (K5, C-308): workflow admission inside `Authorize.authorize`. `Authorize.Input.workflow` (`WorkflowGate(principal, rsSigner, required = false, now)`, the pinned keys) and the per-call `Input.workflowCall` (`WorkflowStep(commitment, receipts, step, units, goalDigest)`; `AuthorizeOptions.workflow` / `run(workflowCall = ...)` for the guards). A call that carries a step is decided by `Workflow.admitStep` over the operation the server will execute and the PCActn's plan root BEFORE the replay claim, so a refusal never consumes the counter: not `allow` is 403 with `workflow` as the only failing check and reason `workflow: <code> (step <id>)`; an `escalate` is `decision = "escalate"`, `allow = false`. No step with `required` is refused (`workflow: this call carries no workflow step (fail closed)`); no step without `required`, or no `workflow` option, changes nothing. Replayed over `authorize-workflow-fixtures.json` (`K5AuthorizeWorkflowTest`).
- Added (K5, C-308): workflow admission through the framework guards. `AuthorizeOptions.workflow` (the pinned `WorkflowGate`) is the guard's workflow option. The per-request step is the host callback (Ktor `workflowStep { call, body -> WorkflowStep? }`; Spring `PcaWorkflowStepMapper`, optional third argument of `PcaFilter` / `PcaInterceptor` and an optional bean in the auto-configuration), else the JSON body member `workflow` (`commitment`, `receipts`, `step`, `units`, `goal_digest`) when the PCActn itself came from the body, else none; a throwing callback or a malformed member is a refused step, never "no step". `PcaGuard.decide` / `execute` and `Operations.Executor.execute` take an optional `workflowCall`. Refusals are those of `authorize` (403, `workflow: edge_relation (step pay)`, ...). Order in `Authorize.authorize`: a configured gate with `required` and no step refuses first (needs no PCActn); a step with an undecodable PCActn is not judged by the gate and the pipeline's own refusal applies. Changed: a present but unreadable PCActn is now refused 401 with failing check `pcactn` and reason `undecodable PCActn: ...` (was check `wire`, `wire: PCActn could not be decoded`); an absent one stays `wire: no PCActn presented`. Tests: `PcaGuardPluginTest`, `PcaSpringTest`.
- Added (K5, C-315..C-319): `ReadVault`: the tokenisation vault (`memoryVault`, `redactReadWithVault`, `detokenize`: a token comes back only for a sink the same signed grant lets its class reach), the aggregate read limits (`aggregateRead` over an explicit state: k-anonymity floor, per-value clamp, query cap, integer micro-epsilon budget, repeats answered free from the state; verification of the signed grant only, this SDK does not sign) and the integer-exact discrete Laplace sampler (`seededDraws`, `secureDraws`, `discreteLaplace`; `noise = "secure"` is the production setting, `"seeded"` is reproducible). Replayed over `vault-aggregate-vectors.json` (`K5VaultAggregateTest`).
- Added (K5): `Workflow` (DAG admission: `admitStep`, `bindPromises`, `planRootAuthorized`, receipt chain, edge constraints, taint, budgets) and `ReadSide` (`redactRead` tighten-only masking, `checkSink`, `readChainLabels`), total and integer-only, replayed over the shared `workflow-vectors.json` and `readside-vectors.json` field for field.

- Added (K9): `Sigstore` verifies a Sigstore bundle offline against a pinned `trusted_root.json` (`parseTrustedRoot`, `verifySigstoreBundleCore`, `verifyRfc3161`): Rekor v1 `dsse`/`intoto` and Rekor v2 `hashedrekord` entries, RFC 3161 and SET time sources, RFC 9162 inclusion to a signed checkpoint, the Fulcio path at every verified time, embedded SCTs, the DSSE signature and the Fulcio identity. `verifySigstoreBundle` returns the SLSA v1 facts `ProvenanceGate.provenanceGate` checks. JCA plus the module's BouncyCastle Ed25519. Replays `sigstore-vectors.json` (`SigstoreVectorsTest`).
- **New (K7, what you see is what you sign):** the canonical approval render (`render`, `H(R)`, the approval challenge, the six-word match code), PSD2 Article 5 linking and the batch commitment, and `render_digest` on escalation requests and answers (the binding refuses an answer for another render, with none, or carrying a render the verifier did not recompute). Replays the shared `approval_*` vectors and the `approval-profiles` vectors byte for byte.
- **Breaking** (unconfirmed means maximally dangerous): a def or schema verb WITHOUT a valid signed human confirmation now has EVERY trait of the registry (`Actions.topTraits`); review state `authored` no longer counts as confirmed. Only an attestation signed by a key pinned with the `reviewer` role (`Actions.reviewerPinsError`, `isConfirmed`, `verbConfirmationError`) sets the effective traits lower. `Actions.effective(def, reg, pins)` gains `confirmed`; `traitsOf(def, reg, pins)` / `hintTraits`; `schemaVerbFloorError` / `schemaFloorError` / `ActionsRegistry.rule22Integrity` take the verifier's reviewer pins (absent = nothing confirmed) and refuse an unconfirmed verb that lacks a trait (`schema_traits_forged: unconfirmed action must carry every trait`). v2 schema verbs may carry a `confirmation` member (`ActionSchema.confirmationShapeError`); `ActionSchema.shapeError(doc, signed = false)` validates an unsigned document. The confirmation also signs `facts_digest` (`Actions.factsDigest(verb)`: the verb minus `traits`, `floors`, `confirmation`, `def`; review domain now `atlas-pca/action-review/v2`), so it counts only for a verb whose own facts are the ones the reviewer saw. Replayed over the `effective`, `schema_verb`, `rule22*` and `schema_shape` vectors.


- Added: `ActionsRegistry`, the registry layer: signed evolution records (`verifyEvolutionRecord`, `evolutionDiffDigest`), principal re-approvals (`reapprovalValid`), the grant pin decision (`decidePin`), signed packs with shards (`verifyPack`), pack inclusion proofs, the rollback tracker (`PackTracker`: chain, version and signatures) and rule 22 over a whole v2 document (`rule22Integrity`, `rule22Decide`). Replayed over the shared registry vectors.
- Added: `Actions`, the action-kit core. Strict ActionDef parse (`validateDef`), `normalize` and the canonical `defDigest`, the 22-trait core registry with custom-trait extension checks (`extendRegistry`, `registryError`), `closure` / `floorOf`, the rule 22 `floorDecision` and the schema integrity check (`schemaVerbFloorError`, `schemaFloorError`, `registryOfSchema`), `traitsDigest` / `tablesDigest`, the pack Merkle root with inclusion proof (`packRoot`, `packProof`, `verifyPackProof`), and `traitsOf` / `declProfile` / `effective`. `ActionSchema` now parses `v: 2` documents (verb `effects`, `traits`, `def`, `floors`; document `traits_digest`, `trait_defs`, `pack`; dotted parameter paths; `role`, `format`, `tags`, `provenance_min`) and checks the new parameter types `datetime`, `duration`, `object_ref` and the string formats in `conform`. A `v: 1` document is validated exactly as before. Replayed over the shared action-kit vectors with exact outcomes.

## 0.4.1

New `primitives.caveat_eval` vectors run in `ConformanceRunner`.

Before, every share `sig` had to be 64 bytes, so a pure ML-DSA-65 share could not be carried. A share's `pq_pk` is still judged only by the threshold check. Reason text is now `threshold.shares[i]: 'sig' is not canonical base64url (N bytes) for alg '<alg>'`. `ConformanceRunner` skips a vector whose `requires` names a registered suite this verifier does not implement.

## Unreleased (BREAKING)

- Depth / R6-05 (parity + robustness): every protocol digest (capHash and the hop body digest, Merkle leaves, params / conditions digests, the threshold signer-set hash) now uses the STRICT canonical form, exactly as the reference `hash.ts` `canonicalBytes`. Before, these were hashed under the lenient form, so a hop or leaf signed over out-of-profile bytes (nesting deeper than 32, a lone surrogate, a non-canonical number) verified where the reference refuses it, and a deeply nested (or cyclic) caveat, Merkle leaf or grant overflowed the stack: the `StackOverflowError` escaped `verifyChain` / `verifyInclusion` / `verifyPcactn` (they catch only `RuntimeException`). The public lenient `Json.canonicalize` is capped at `Json.MAX_LENIENT_DEPTH` (512). Shared `primitives.depth` vectors (limit-1 / limit / limit+1 / 100000 per entry point) run in the conformance runner on a 512 KiB stack.
- R6-03/R6-04 (parity): `Threshold.verifyShare` validates the WHOLE signer set like the reference (unknown / wrong-case roles, malformed keys, empty / null / short `pq_pk` anywhere, one key per role, one role per key, a duplicate (role, key) only with the same `pq_pk`); `t` must be 1, 2 or 3; `share.role` is required. New total `Threshold.verifyShareEntry(Any?)` and `Threshold.signerSetHashB64u(Any?)` (UTF-8 byte order, `pq_pk` whenever a string).
- R6-05 (robustness / parity): `Pca.verifyChain` applies the reference per-hop type check (`wellTyped`: a correctly signed hop with ill-typed caveats, `holder`, `holder_pq` or a numeric `pq_pk` was ACCEPTED before) and is total; `Pca.verifyPcactn` is total. Round-6 shared vectors (`threshold_set`, `signer_set_hash`, `malformed`) run in `ConformanceRunner`.
- R6-02 (security): a signer-set role that registers a `pq_pk` now REQUIRES a PQ (pure or hybrid) threshold share; an ed25519-only share for that role is refused, so an Ed25519 break no longer forges a hybrid-registered role (parity with the TypeScript reference). Corpus: `agent-bound-signerset-with-pq-pk` is now `valid:false`; new positive `agent-hybrid-signerset-with-pq-pk`.
- R5-A1 (security): threshold-share verification is now signer-set PINNED, no longer self-vouched. The share must be for the one key the signer set registers for its role, a PQ/hybrid share verifies only under the set's registered `pq_pk` (a differing share `pq_pk` is refused), the share-suite tag is part of the signed bytes (a classical share cannot be relabelled hybrid), and the signer-set hash now includes a registered `pq_pk` (parity with the TypeScript reference). New corpus vectors: `agent-not-in-signer-set`, `agent-bound-signerset-with-pq-pk`, `agent-hybrid-relabel-*`.
- R5-B2k: `PinnedPq` (and `Pq.verifySuite`) are now module-internal; the public `PinnedPq.resolve` let any caller mint a pinned key from the artifact's own `pq_pk`.

- Suite policy defaults documented: no list = no restriction, an empty list refuses everything, and the hosted API defaults to ed25519 + Ed25519 hybrids (README lists the exact list to pass offline).

- R4-01: `Pca.verifyChain` now takes the root's PQ authority from the verifier, exactly like the TypeScript reference (R3-01). Two new trailing parameters, `pqPins: Map<String, Any?>?` (root issuer Ed25519 b64u -> PQ public key) and `trustedRoot: Map<String, Any?>?` (the verifier's own stored root capability). A non-ed25519 (pure `ml-dsa-65` or hybrid) ROOT hop is accepted only if `pqPins[root.issuer]` equals the root's `pq_pk`, or `trustedRoot` is the root itself (same content hash). Otherwise it is refused with `hop 0: root suite '<alg>' needs a PQ key pinned for the root issuer (policy.pqPins) or the verifier's stored grant (policy.trustedRoot); the root's own pq_pk proves nothing about who issued it (R3-01)`. Before, a pure-PQ root signed with the attacker's own ML-DSA key but naming a victim Ed25519 issuer verified. Callers of `verifyChain` on a root they did not load from their own store must now pass `pqPins`. `verifyPcactnCore` is unchanged in behaviour (it passes its grant as `trustedRoot`). Internally `PinnedPq.resolve` is the single choke point: `PinnedPq` has a private constructor and is the only key type `Pq.verifySuite` accepts, so the PQ verify cannot be called with an artifact key. `Pq.verifyLeafSuite` remains as an explicitly caller-vouched overload for threshold shares and `pq_artifact` signatures.
